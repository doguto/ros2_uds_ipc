# Benchmark

`ros2_uds_ipc` と DDS (Fast DDS / Cyclone DDS)・Zenoh の、レイテンシ・CPU 使用量・メモリ・接続時間の比較と、その計測方法です。
[README](../README_ja.md) に戻る。

## 概要

2 プロセス間、1 KB のペイロード、1 kHz での、`publish()` から subscriber のコールバックまでのレイテンシ中央値 (µs、括弧内は p99) です。

| 方式 | 無負荷 | busy loop 4 本 |
|---|---|---|
| UDS (fixed-size) | 135 (178) | 12.0 (22.9) |
| UDS (variable-size) | 128 (203) | 14.7 (39.6) |
| DDS (Fast DDS) | 236 (333) | 712 (3128) |
| DDS (Cyclone DDS) | 213 (390) | 152 (1944) |
| Zenoh | 344 (496) | 967 (3221) |

無負荷の数値は、CPU が深いアイドル状態から復帰する時間が支配的です。負荷時には、DDS と Zenoh のミドルウェア層の分が
差として残ります。アイドル状態を C1 までに制限すると (256 B、1 kHz)、UDS の無負荷時のレイテンシは負荷時と同程度の
15 µs (固定長) と 34 µs (可変長) まで下がり、DDS と Zenoh は 144〜272 µs にとどまります
([詳細](#cpu-のアイドル状態))。

負荷時の裾は、方式よりもスケジューリングの問題です。受信経路のスレッドがときどき他の処理の後ろで待たされるため、
1 回の実行の最大レイテンシは、どの方式でも 2〜5 ms になります。リアルタイム優先度を付けると、これがなくなります。
付けた場合 (256 B、1 kHz) の最大レイテンシは次のとおりです。

| 方式 | 最大レイテンシ | リアルタイムにしたもの |
|---|---|---|
| UDS (fixed-size) | 27 µs | 受信スレッドと送信スレッド |
| UDS (variable-size) | 57 µs | 受信スレッドと送信スレッド |
| DDS (Cyclone DDS) | 95 µs | publisher と subscriber のプロセス全体 |
| DDS (Fast DDS) | 115 µs | publisher と subscriber のプロセス全体 |
| Zenoh | 145 µs | publisher と subscriber のプロセス全体 |

UDS のほうが速いままで、差はおよそ 2 倍 (可変長) から 5 倍 (固定長) です。優先度を付けるスレッドも 1 本で済みます。指定は
[コンストラクタの引数](../README_ja.md#リアルタイムスケジューリング)で行います ([詳細](#リアルタイムスケジューリング))。

## 計測方法

`ros2_uds_ipc_benchmark` パッケージで計測しました。publisher ノードと subscriber ノードを別プロセスで起動し、
ペイロード 6 種 x 送信レート 4 種 (100 Hz / 1 kHz / 10 kHz / 無制限) を、無負荷と、busy loop スレッド 4 本
(ハードウェアスレッド数と同じ) と CPU を奪い合う状態の両方で測っています。表とグラフは各条件 5 回の実行の中央値です。
環境は Intel Core i5-3427U (4 スレッド)、Linux 7.0.0-31-generic、ROS 2 Jazzy で、
[リアルタイムスケジューリング](#リアルタイムスケジューリング)の節を除き、CPU 固定やリアルタイムスケジューリングは行っていません。

| 系列 | メッセージ | シリアライズ | 受信キューが満杯のとき |
|---|---|---|---|
| **UDS (variable-size)** | `std_msgs/UInt8MultiArray` | CDR | `publish(msg, 1s)` が subscriber を待つ |
| **UDS (fixed-size)** | `uint8[N]` (`msg/Fixed<N>.msg`) | なし。メッセージをそのまま送る | `publish(msg, 1s)` が subscriber を待つ |
| **DDS (Fast DDS)** | `std_msgs/UInt8MultiArray` | CDR | reliable + keep-all (`rmw_fastrtps_cpp`) |
| **DDS (Cyclone DDS)** | `std_msgs/UInt8MultiArray` | CDR | reliable + keep-all (`rmw_cyclonedds_cpp`) |
| **Zenoh** | `std_msgs/UInt8MultiArray` | CDR | reliable + keep-all (`rmw_zenoh_cpp`、ローカルの `rmw_zenohd` ルーター経由) |

UDS はどちらも send timeout 付きで、メッセージは届くか、失敗として報告されるかのどちらかです。黙って捨てることはありません。
ノンブロッキングの `publish(msg)` (`transport:=uds`) は既定の計測には含めていません。キューが満杯にならないレートでは同じ性能です。
DDS と Zenoh は通常の `rclcpp` publisher / subscription で、トランスポートはデフォルトです。

生データ: [`latency.csv`](benchmark/latency.csv) — 全 1200 件の計測 (240 条件 x 5 回)。

## 補足

- **シリアライズを省くと速くなります。** 固定長メッセージは可変長に比べて 1 割〜3 割速く、100 Hz の無負荷で 170〜178 µs 対 184〜234 µs、
  10 kHz の無負荷で 30 µs 対 36 µs (1K)、負荷ありの 1 kHz で 12 µs 対 15 µs です (64 B〜1K)。
  差はペイロードが大きくなると広がります (64K、100 Hz 無負荷で 295 µs 対 422 µs)。対象は、プリミティブと
  固定長配列だけで構成されたメッセージです。
- **UDS は無負荷のほうが遅くなります** (100 Hz で 184 µs 対 16 µs)。ほかに何も動いていないと、メッセージの合間に CPU が
  深いアイドル状態に入り、その復帰がレイテンシの大半を占めます。busy loop がコアを起こし続けるため、
  負荷ありのほうが速くなります。制限したときの効果は [CPU のアイドル状態](#cpu-のアイドル状態) を参照してください。
- **負荷時は、UDS とミドルウェアの差が大きく開きます** (1 kHz、1K で 10〜80 倍)。DDS / Zenoh は受信経路で複数スレッドが順に
  スケジュールされる必要があるためです。
- **負荷ありの 10 kHz はマシンが飽和しています** (4 スレッドに busy loop 4 本)。UDS はスケジューリングに支配されて
  ばらつくため、系列間の差は読み取れません。
- **Fast DDS の 10 kHz・64K と無制限レート**では、メッセージがキューに溜まる (reliable + keep-all) ため、レイテンシ列は
  トランスポートの速さではなくキューでの待ち時間 (最大で秒単位) を表します。負荷ありでは、これらの条件の 5 回中 3〜4 回が
  最後まで終わりませんでした (subscriber が 10 秒間メッセージを受け取れず諦めた)。計り直しても同じだったため、
  中央値からは除き、「完了しなかった実行」に載せています。

## レート無制限の条件

できる限り速く送ると、CSV のレイテンシ列はトランスポートの速さではなく、メッセージがキューで待った時間を表します。
DDS (reliable + keep-all) と Zenoh は全部キューに溜めるため、この条件の中央値はミリ秒から秒単位になります。
send timeout 付きの UDS はソケットバッファが満杯になると publisher が待つため、レイテンシは低く保たれます。

## メッセージの取りこぼし

`publish()` が送れなかった (`false` を返した) メッセージの割合です。send timeout 付きの UDS と DDS / Zenoh は、
全条件で取りこぼしがありませんでした。ノンブロッキングの `publish(msg)` はキューが満杯になると `false` を返しますが、
既定の計測には含めていません。

## リアルタイムスケジューリング

リアルタイム優先度が、負荷時のレイテンシに与える効果です。256 B を 1 kHz と 100 Hz で、busy loop スレッド 4 本と CPU を
奪い合う状態で測っています。各セルは「既定のスケジューリング → `SCHED_FIFO` 優先度 40」(µs) で、5 回の実行の中央値です。
「5 回中の最悪値」は、5 回のうちで最も大きかったレイテンシです。2 つの設定は交互に測りました。

- **UDS** — 受信スレッド (`Scheduling::rt_priority`、[README](../README_ja.md#リアルタイムスケジューリング) を参照) と
  送信スレッドだけ。プロセス内のほかのスレッドは既定のままです。
- **DDS / Zenoh** — publisher と subscriber のプロセス全体を `chrt -f 40` で起動し、ミドルウェアの全スレッドに優先度を
  付けています。これらにとって最も有利な設定です。Zenoh のルーターは既定のままです。

| Zenoh | 664 → 95 | 3612 → 154 | 4615 → 213 | 4615 → 229 | 15632 → 265 | 176 → 167 |

- **裾は、どの方式でもスケジューリングの問題です。** 既定のスケジューリングでは、受信経路のスレッドがときどき busy loop
  スレッドの後ろで待たされ、1 回の実行の最大レイテンシは方式によらず 1〜5 ms になります。リアルタイム優先度を付けると、
  すべての方式で 300 µs 未満に収まり、1 kHz の制御周期に十分間に合います。
- **すべてをリアルタイムにしても、UDS のほうが速いままです。差はおよそ 2 倍 (可変長) から 5 倍 (固定長) です。** 1 kHz での最大レイテンシは 27 µs (固定長) と 57 µs (可変長) で、
  他は 95〜145 µs です。中央値は 11 µs と 27 µs に対して 50〜91 µs、1 メッセージあたりの CPU 時間は 32 µs と 51 µs に対して
  92〜158 µs です。
- **UDS は、優先度を付けるスレッドが 1 本で済みます。** DDS の数値はプロセス全体をリアルタイムにした結果で、重い処理も行う
  プロセスでは使えません。受信経路のスレッドだけに優先度を付けるには、ミドルウェアごとの設定が必要です。
- **リアルタイム優先度を付けない場合** (設定できない環境など) は、p99 に差が出ます。1 kHz で、UDS の 35〜71 µs に対して
  1.7〜2.9 ms です。
- 100 Hz の実行は 1000 メッセージなので、p99.9 と最大値は 1 サンプルの値です。

生データ: [`latency_rt.csv`](benchmark/latency_rt.csv) (`rt_priority` が 0 と 40、各 50 回)。再現するには、
`run_latency_matrix.sh` に `RT_PRIORITY=40` を渡します。プロセスに `rtprio` の上限設定が、Zenoh には起動済みのルーターが必要です。

## CPU のアイドル状態

無負荷の数値が負荷ありより大きい理由と、CPU のアイドル状態 (C-state) を制限したときの効果です。無負荷、256 B を
1 kHz と 100 Hz で測っています。各セルは「C7 (既定) → C1E → C1」(CPU に許した最も深いアイドル状態) の順で、
3 回の実行の中央値 (µs) です。3 つの設定は交互に測りました。制限には PM QoS を使っています。プロセスが
`/dev/cpu_dma_latency` を開いたまま、許容する復帰時間の上限 (この CPU では C1E が 10 µs、C1 が 1 µs) を書き込みます。

| 設定 | アイドル時間に占める C1 の割合 | C1E | C3 | C7 |
|---|---|---|---|---|
| C7 (既定) | 0.2% | 2.0% | 2.8% | 95.0% |
| C1E | 0.6% | 99.4% | 0% | 0% |
| C1 | 100% | 0% | 0% | 0% |

### 1 kHz

| 方式 | 中央値 | p99 | 1 メッセージあたり CPU 時間 |
|---|---|---|---|
| UDS (fixed-size) | 134 → 34 → 15 | 172 → 58 → 51 | 207 → 88 → 54 |
| UDS (variable-size) | 184 → 83 → 34 | 300 → 118 → 115 | 254 → 150 → 83 |
| DDS (Cyclone DDS) | 205 → 158 → 144 | 274 → 231 → 199 | 294 → 248 → 182 |
| DDS (Fast DDS) | 242 → 191 → 185 | 453 → 247 → 230 | 410 → 326 → 253 |
| Zenoh | 358 → 286 → 272 | 467 → 357 → 321 | 505 → 425 → 355 |

### 100 Hz

| 方式 | 中央値 | p99 | 1 メッセージあたり CPU 時間 |
|---|---|---|---|
| UDS (fixed-size) | 170 → 38 → 35 | 190 → 82 → 64 | 361 → 104 → 80 |
| UDS (variable-size) | 338 → 96 → 84 | 437 → 186 → 161 | 570 → 175 → 140 |
| DDS (Cyclone DDS) | 619 → 166 → 169 | 709 → 290 → 243 | 852 → 282 → 269 |
| DDS (Fast DDS) | 642 → 230 → 198 | 758 → 328 → 280 | 1104 → 412 → 344 |
| Zenoh | 979 → 299 → 304 | 1114 → 415 → 407 | 1323 → 472 → 440 |

- **UDS の無負荷時のレイテンシは、CPU の復帰時間です。** 既定では、アイドル中のコアは時間の 95% を C7 で過ごし、
  メッセージのたびにそこから復帰します。C1 までに制限すると、UDS (固定長) は 1 kHz で 134 µs から 15 µs になり、
  busy loop がコアを起こし続けている負荷時 (12 µs) とほぼ同じになります。
- **C1E までの制限でも、効果の大半が得られます。** 1 kHz で 134 µs から 34 µs になり、100 Hz では C1E と C1 の差は
  ほとんどありません。
- **DDS と Zenoh は下がり幅が小さく**、C1 でも 1 kHz で 144〜272 µs です。そのため、この中で最も速い Cyclone DDS と UDS の差は、
  固定長で 1.5 倍から約 10 倍に、可変長で 1.1 倍から約 4 倍に開きます。これ以上下がらない理由は調べていません。アイドル時に下がる
  CPU 周波数も、条件として揃えていません。
- アイドル状態を制限すると、アイドル時の消費電力が上がります (未計測)。制御専用のマシンでは一般的な設定で、
  上記の PM QoS か、カーネルパラメータで行います。
- 各設定 3 回の実行です。最大値は実行ごとのばらつきが大きいため、載せていません。

生データ: [`latency_idle_states.csv`](benchmark/latency_idle_states.csv) (90 回。設定は `deepest_idle_state` 列)。

## CSV の列

| 列 | 意味 |
|---|---|
| `transport`, `rmw` | `uds` / `uds_reliable` / `uds_reliable_fixed` / `dds`。`dds` の場合は RMW 実装 (`rmw_fastrtps_cpp` / `rmw_cyclonedds_cpp` / `rmw_zenoh_cpp`) |
| `payload_bytes`, `rate_hz`, `load_threads` | 計測条件。`rate_hz` の 0 は無制限 |
| `count`, `publish_failed`, `received` | publish した数、送れなかったと報告された数、受信した数 |
| `min_us` ... `max_us` | `publish()` の直前から subscriber のコールバックまでのレイテンシ |
| `pub_cpu_percent`, `sub_cpu_percent` | 各プロセス (全スレッド) の CPU 使用率。100 = 1 コア |
| `pub_cpu_us_per_msg`, `sub_cpu_us_per_msg` | 各プロセスの 1 メッセージあたり CPU 時間 |
| `connect_ms` | publisher を生成してから subscriber に届く状態になるまで |
| `pub_max_rss_kb`, `sub_max_rss_kb` | 各プロセスの最大 RSS |
| `throughput_hz` | 毎秒の受信メッセージ数 |
| `rt_priority` | `SCHED_FIFO` 優先度。使わない場合は 0 (新しいファイルのみ)。`uds` は受信スレッドと送信スレッド、`dds` はプロセス全体 |

## 自分で計測する

計測ツールは別パッケージ `ros2_uds_ipc_benchmark` に分離しており、`ros2_uds_ipc` のバイナリには含まれません。
UDS と通常の DDS pub / sub のプロセス間レイテンシと、publisher / subscriber 各プロセスの CPU 使用率・最大メモリ使用量、
publish 失敗数、接続確立までの時間を同一条件で計測し、結果を CSV で出力します。CPU に負荷をかけた状態 (`load_threads`) での計測もできます。

```bash
colcon build --packages-up-to ros2_uds_ipc_benchmark
source install/setup.bash

# 単一条件 (transport: uds / uds_reliable / uds_reliable_fixed / dds)
ros2 launch ros2_uds_ipc_benchmark latency.launch.py transport:=uds payload_bytes:=1024 count:=10000 rate_hz:=1000.0

# 同条件で、busy loop スレッド 8 本と CPU を奪い合う状態
ros2 launch ros2_uds_ipc_benchmark latency.launch.py transport:=uds payload_bytes:=1024 load_threads:=8

# CPU 負荷 x transport x 送信レート x ペイロードサイズ (LOADS / RATES / SIZES / COUNT / RMWS で上書き可能) を 5 回ずつ
# dds はインストール済みの RMW 実装ごとに計測
REPEAT=5 ros2 run ros2_uds_ipc_benchmark run_latency_matrix.sh result.csv

# CSV をグラフ化。繰り返し実行した条件は中央値を描く (matplotlib が必要)
ros2 run ros2_uds_ipc_benchmark plot_latency.py result.csv charts/

# CSV を、このページの全表を含む Markdown レポートにする
ros2 run ros2_uds_ipc_benchmark report_latency.py result.csv benchmark.md
```

ビルド、インストール済みの全 RMW (Zenoh ルーターの起動を含む) での計測、グラフとレポートの生成までを一度に行うには:

```bash
scripts/run_all_benchmarks.sh   # benchmark_result/<タイムスタンプ>/ に出力
```
